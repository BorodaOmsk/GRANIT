# Качество: Definition of Done и критерии приёмки

В госконтракте «готово» для команды и «готово» для заказчика — разные вещи, и расхождение всплывает на приёмке, когда исправлять уже дорого. Этот документ вводит трёхслойную систему качества, чтобы «готово» означало одно и то же для всех.

---

## Три слоя качества

```
┌─────────────────────────────────────────────────────────┐
│ СЛОЙ 3: Критерии приёмки ВЕХИ (контракт)                 │
│   Соответствие ТЗ, ГОСТам, приёмо-сдаточные испытания    │
├─────────────────────────────────────────────────────────┤
│ СЛОЙ 2: Definition of Done ИНКРЕМЕНТА/ИТЕРАЦИИ (команда) │
│   Универсальный чек-лист качества для любой задачи       │
├─────────────────────────────────────────────────────────┤
│ СЛОЙ 1: Критерии приёмки ЗАДАЧИ (Acceptance Criteria)    │
│   Функциональные условия конкретной задачи               │
└─────────────────────────────────────────────────────────┘
```

**Ключевое различие** (частая путаница):
- **Acceptance Criteria (AC)** — ЧТО должна делать конкретная задача (функциональные условия). Пишутся для каждой задачи.
- **Definition of Done (DoD)** — КАКОГО качества должна быть ЛЮБАЯ работа (универсальные стандарты). Один на команду/проект.
- **Критерии приёмки вехи** — контрактные условия сдачи результата заказчику.

Задача «готова», только когда выполнены и её AC, и общий DoD. Веха сдаётся, когда все её задачи Done и выполнены контрактные критерии приёмки.

---

## Слой 1. Критерии приёмки задачи (Acceptance Criteria)

Пишет владелец продукта до взятия задачи в работу. Формат — сценарный:

```
Дано (контекст) → Когда (действие) → Тогда (ожидаемый результат)
```

Правила:
- AC формулируются до начала разработки (иначе непонятно, что оценивать).
- Проверяемы: каждый пункт можно однозначно проверить «да/нет».
- Согласованы с куратором заказчика для контрактно-значимых задач.

---

## Definition of Ready (DoR): входной фильтр задачи

Если DoD отвечает на вопрос «когда работа *закончена*», то **Definition of Ready** отвечает на зеркальный вопрос — «когда задача (в том числе вброс) *готова к взятию* в оценку и работу». Для методологии, чья суть — фильтрация вбросов, DoR это «входной DoD»: он не пускает в работу сырые, непонятные или нелегитимные задачи и тем самым защищает поток ещё до расходования ёмкости.

Базовый DoR ГРАНИТ (задача не берётся в итерацию, пока не выполнено):

- [ ] Задача зарегистрирована через Единое окно (для вбросов — с автором через куратора заказчика, см. [04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md))
- [ ] Суть и ценность понятны команде, сформулированы AC
- [ ] Классифицированы тип и критичность (для вбросов), определена связь с объёмом контракта
- [ ] Внешние зависимости выявлены и не блокируют старт
- [ ] Задача оценена командой и помещается в доступную ёмкость (буфер или контрактный поток)
- [ ] Для контрактно-значимых задач — AC согласованы с куратором заказчика

> DoR и DoD — две границы одной задачи: DoR на входе, DoD на выходе. Вброс, не прошедший DoR, не «зависает в работе», а возвращается в Единое окно на доработку/оценку — это и есть дисциплина против сырых вбросов и незавершёнки (WIP).

## Слой 2. Definition of Done (DoD)

Универсальный чек-лист. Для госконтракта DoD **обязан** включать пункты соответствия, а не только «код написан». Базовый DoD ГРАНИТ:

**Разработка**
- [ ] Код написан и соответствует принятым стандартам кодирования
- [ ] Проведено код-ревью
- [ ] Написаны и проходят автотесты (покрытие не ниже установленного порога)
- [ ] Нет критичных замечаний статического анализа

**Соответствие и безопасность**
- [ ] Соответствует применимым ГОСТ/регламентам/ТЗ
- [ ] Выполнены требования информационной безопасности (в т.ч. ИБ-ревью для критичных модулей)
- [ ] Проверена совместимость с целевой платформой (например, отечественная ОС/СУБД)

**Документация**
- [ ] Обновлена эксплуатационная и техническая документация
- [ ] Обновлена матрица требований (трассировка ТЗ → реализация)

**Проверка**
- [ ] Проведено функциональное тестирование по AC
- [ ] Проведена демонстрация владельцу продукта
- [ ] Дефекты уровня «блокер/критичный» отсутствуют

> DoD фиксируется в начале проекта, согласуется с заказчиком и пересматривается на ретроспективах инкремента. Меняется осознанно, а не по ходу.

### Многоуровневый DoD (при нескольких командах)
DoD не обязан быть одним жёстким списком для всех. Допустимы уровни: DoD задачи → DoD итерации → DoD инкремента (интеграция, сквозное тестирование, готовность к приёмке). Общая часть (соответствие, ИБ, документация) — единая для всех команд.

## Слой 3. Критерии приёмки вехи

Контрактный уровень. Формируются из ТЗ на этапе планирования вехи (см. [03_ЖИЗНЕННЫЙ_ЦИКЛ.md](03_ЖИЗНЕННЫЙ_ЦИКЛ.md)) и проверяются на гейте соответствия перед госприёмкой. Включают:
- полноту реализации всех пунктов ТЗ, отнесённых к вехе;
- прохождение приёмо-сдаточных испытаний (ПСИ);
- комплект сдаточной документации;
- закрытые замечания предыдущих приёмок.

---

## Связь качества с вбросами

Вбросы — главный враг качества: спешка ведёт к пропуску пунктов DoD. Защита:
1. Вброс, взятый в буфер, проходит **тот же DoD**, что и плановая задача. «Быстро и без документации» запрещено — это скрытый техдолг и риск на приёмке.
2. Если вброс физически не может пройти полный DoD в срок — это аргумент для CCB перенести его, а не снижать качество.
3. Дефекты (несоответствие уже принятому DoD/AC) не расходуют буфер вбросов — это обязательство по качеству, они идут вне буфера (см. [04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md)).

---

## Управление качеством в ритме

| Точка | Что проверяем |
|-------|---------------|
| Планирование итерации | Задача проходит DoR (готова к взятию) |
| Планирование задачи | Есть AC, они проверяемы |
| Ежедневная синхронизация | Нет задач, «застрявших» на пунктах DoD |
| Демо итерации | Задачи соответствуют AC и DoD |
| Гейт соответствия | Веха соответствует критериям приёмки (слой 3) |
| Ретроспектива инкремента | Пересмотр DoD по фактическим дефектам |

> Метрики качества (дефекты после приёмки, возвраты на гейте) — см. [07_МЕТРИКИ.md](07_МЕТРИКИ.md).
