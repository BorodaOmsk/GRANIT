# Технологические ограничения и импортозамещение

Для компаний с госучастием технологический стек — не свободный выбор, а требование. Использование иностранного ПО может быть прямо запрещено условиями контракта или нормативными актами, а несоответствие вскрывается на приёмке, когда переделка стоит дорого. Поэтому технологические ограничения в ГРАНИТ — это входное условие, встроенное в качество и риски.

---

## Принцип: соответствие проверяется на входе, а не на приёмке

Технологический выбор фиксируется в начале и проверяется постоянно (пункт DoD, см. [10](10_КАЧЕСТВО_И_DOD.md)), а не «когда дойдём до сдачи». Обнаружить несовместимость с целевой платформой за неделю до госприёмки — это гарантированный срыв вехи.

---

## Реестр технологического стека проекта

Ведётся с самого старта. Для каждого компонента:

| Поле | Пример |
|------|--------|
| Компонент | СУБД, ОС, среда исполнения, библиотека |
| Выбранное решение | Отечественная ОС / отечественная СУБД |
| Статус соответствия | В реестре отечественного ПО / требует замены / под вопросом |
| Ограничения контракта/НПА | Требование использовать реестровое ПО |
| План при запрете иностранного | На какой аналог мигрируем |
| Риск | Уход вендора, отзыв из реестра, несовместимость |

Это одновременно артефакт и вход для реестра рисков ([11](11_УПРАВЛЕНИЕ_РИСКАМИ.md)). Реестр стека и решения по платформе — часть архитектурных решений: фиксируйте их в ADR/базе знаний ([14](14_ЗНАНИЯ_И_КОМАНДА.md)), чтобы обоснование выбора не терялось при смене команды.

---

## Проверка совместимости

Целевая платформа проверяется рано и регулярно:

1. **Прототип на целевой платформе** в первом же инкременте, где это критично. Не «разработаем на привычном, потом перенесём» — перенос всегда дороже ожидаемого.
2. **Целевая среда в конвейере** — сборка и тесты прогоняются на целевой ОС/СУБД, а не только на машинах разработчиков.
3. **Пункт DoD**: «проверена совместимость с целевой платформой» — обязателен для контрактов с требованием импортозамещения.

---

## Управление миграцией (если заменяем иностранное)

Когда в ходе проекта иностранный компонент нужно заменить (запрет, уход вендора, требование заказчика):

```
1. Зафиксировать через Единое окно как изменение ([04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md))
2. Оценить влияние: трудозатраты, риск, сдвиг вех (карточка влияния)
3. Решение CCB: буфер / инкремент / допсоглашение
4. Выбрать отечественный аналог, проверить на прототипе
5. Спланировать миграцию как отдельные задачи с DoD
```

Замена платформы почти всегда — это изменение объёма. Не поглощайте её молча за счёт буфера вбросов, если она масштабная: это повод для допсоглашения о сроках.

## Связь с другими контурами

| Контур | Связь с импортозамещением |
|--------|---------------------------|
| Качество ([10](10_КАЧЕСТВО_И_DOD.md)) | Совместимость с платформой — пункт DoD |
| Риски ([11](11_УПРАВЛЕНИЕ_РИСКАМИ.md)) | Уход вендора, отзыв из реестра — отдельные риски |
| Изменения ([04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md)) | Требование сменить стек — через CCB |
| Субподряд ([16](16_СУБПОДРЯДЧИКИ.md)) | Стек субподрядчика тоже должен соответствовать |
| Приёмка ([13](13_ИНИЦИАЦИЯ_И_ПРИЁМКА.md)) | Соответствие стека проверяется на внутреннем гейте соответствия ([06](06_ЦЕРЕМОНИИ_И_АРТЕФАКТЫ.md)) до госприёмки |

> Конкретные наименования реестрового ПО и нормативные требования зависят от контракта и меняются со временем — держите реестр стека актуальным и сверяйтесь с действующими нормами на момент проекта.
