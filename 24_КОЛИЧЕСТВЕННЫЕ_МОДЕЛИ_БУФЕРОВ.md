# Количественные модели буферов

Базовый расчёт буферов ([05](05_ПЛАНИРОВАНИЕ_И_БУФЕРЫ.md)) даёт стартовый ориентир (15–25% ёмкости) и правило «пересчёт по факту через 2–3 инкремента». Этого достаточно для уровней зрелости L2–L3 ([19](19_МОДЕЛЬ_ЗРЕЛОСТИ.md)). Но на L4–L5, когда накоплена статистика, «средний расход + 5%» — грубоватая оценка: она игнорирует **разброс** потока вбросов. Этот раздел даёт количественные модели для тех, кто хочет считать буфер не по среднему, а по вероятности срыва.

> **Когда это нужно.** Если буфер стабильно в 🟢/🟡 и вехи сдаются — не усложняйте, среднего достаточно (принцип 8, минимум лишнего). Количественные модели включают, когда: (а) поток вбросов «рваный» (то пусто, то вал), (б) цена срыва вехи высока (крупная неустойка), (в) заказчик требует обоснования размера буфера цифрами, а не «опытом».

---

## Почему среднего недостаточно: разброс важнее среднего

Два заказчика с одинаковым **средним** потоком вбросов (например, 10 SP за итерацию) могут требовать совершенно разного буфера:

- **Заказчик А (ровный):** каждую итерацию приносит 9–11 SP. Буфер 12 SP почти всегда покрывает — риск пробоя низкий.
- **Заказчик Б (рваный):** три итерации по 2 SP, потом вал на 34 SP. Среднее те же 10 SP, но буфер 12 SP регулярно пробивается на «валах».

Вывод: **буфер защищает не от среднего, а от колебаний.** Размер буфера должен зависеть от разброса (стандартного отклонения) потока, а не только от его центра. Именно это и делают модели ниже.

```
Поток вбросов (SP за итерацию)
  А (ровный):   ▁▂▂▁▂▂▁▂▂▁   среднее 10, разброс низкий → буфер ≈ 12
  Б (рваный):   ▁▁█▁▁█▁▁█▁   среднее 10, разброс высокий → буфер ≈ 20+
                              (тот же средний поток — вдвое больший буфер)
```

## Модель 1. Буфер по перцентилю (простая, «на калькуляторе»)

Первый шаг за пределы среднего — считать буфер не по среднему, а по **целевому перцентилю** фактического расхода. Это не требует симуляций, только историю расхода буфера за прошлые итерации.

### Как считать

1. Соберите фактический расход буфера (в SP или часах) за N прошлых итераций — эти данные уже есть в реестре изменений ([04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md), [07](07_МЕТРИКИ.md)).
2. Отсортируйте значения по возрастанию.
3. Выберите **целевой уровень сервиса** — какую долю итераций буфер должен покрывать без пробоя:

| Целевой уровень покрытия | Перцентиль | Когда применять |
|--------------------------|-----------|-----------------|
| 80% итераций | P80 | Обычная веха, умеренная цена срыва |
| 90% итераций | P90 | Веха с ощутимой неустойкой |
| 95% итераций | P95 | Критичная веха, большой штраф, репутационный риск |

4. Буфер = значение расхода на выбранном перцентиле.

### Пример

Расход буфера за 10 итераций (SP): `4, 6, 6, 8, 8, 10, 12, 14, 20, 30`.

- Среднее = 11.8 → «среднее + 5%» дало бы буфер ≈ 12 SP.
- P80 (8-е из 10 значений) = 14 SP.
- P90 (9-е значение) = 20 SP.

Разница между 12 и 20 SP — это и есть «слепая зона» среднего: планируя буфер 12 SP, вы сознательно принимаете ~30% итераций с пробоем буфера.

> **Правило:** документируйте выбранный перцентиль в плане инкремента. «Буфер 20 SP = покрытие P90, то есть 1 итерация из 10 может пробить буфер и потребовать решения CCB» — честная, защищаемая формулировка для заказчика и руководства.

## Модель 2. Монте-Карло симуляция (для «рваного» потока и высокой цены срыва)

Когда поток вбросов нерегулярный, а цена срыва высока, перцентиля по 10 точкам мало — выборка слишком короткая. Монте-Карло позволяет «проиграть» тысячи возможных вариантов будущего на основе распределения прошлых вбросов и получить **вероятность пробоя буфера** для любого его размера.

### Идея метода

Вместо одного «среднего» сценария симулятор:
1. многократно (10 000+ раз) «разыгрывает» случайный поток вбросов на инкремент, беря значения из распределения прошлых вбросов;
2. для каждого розыгрыша проверяет, пробил бы буфер данного размера или нет;
3. считает долю розыгрышей с пробоем = **вероятность срыва** при этом буфере.

Дальше вы выбираете буфер под приемлемую вероятность срыва (например, «не более 10% инкрементов с пробоем»).

### Что нужно на входе

- История вбросов: по каждому — трудозатраты (SP) и итерация поступления. Из реестра изменений.
- Ёмкость команды на инкремент (SP).
- Длина инкремента в итерациях.

### Референс-реализация (Python)

> Скрипт — самостоятельный инструмент аналитика/РП, запускается офлайн на выгрузке из трекера (CSV из фильтра реестра изменений, [23](23_ИНСТРУМЕНТАРИЙ.md)). Не требует установки в Jira. Адаптируйте под свои данные.

```python
"""
Монте-Карло оценка буфера вбросов для ГРАНИТ.
Вход: история трудозатрат вбросов по итерациям (SP).
Выход: вероятность пробоя буфера для набора кандидатных размеров.
"""
import random
import statistics

# --- ВХОДНЫЕ ДАННЫЕ (замените своими из реестра изменений) ---
# Список: сколько вбросов приходило в каждой прошлой итерации
inflow_counts_per_iteration = [3, 1, 5, 2, 0, 4, 6, 2, 3, 1]
# Пул трудозатрат отдельных вбросов (SP), наблюдённых исторически
inflow_sizes = [1, 2, 2, 3, 3, 3, 5, 5, 8, 8, 13]

ITERATIONS_PER_INCREMENT = 4      # 8-недельный инкремент = 4 итерации по 2 нед
SIMULATIONS = 200000              # число розыгрышей
CANDIDATE_BUFFERS = [8, 12, 16, 20, 24, 30, 36]  # кандидатные размеры буфера на ИТЕРАЦИЮ (SP)

def simulate_one_iteration():
    """Разыгрывает суммарный поток вбросов за одну итерацию."""
    n = random.choice(inflow_counts_per_iteration)      # сколько вбросов
    return sum(random.choice(inflow_sizes) for _ in range(n))  # их суммарный объём

def probability_of_iteration_breach(buffer_per_iteration, demand):
    """Доля итераций, в которых спрос превысил буфер."""
    return sum(1 for d in demand if d > buffer_per_iteration) / len(demand)

if __name__ == "__main__":
    demand = [simulate_one_iteration() for _ in range(SIMULATIONS)]
    ordered = sorted(demand)
    print(f"Спрос на буфер за итерацию (SP): "
          f"среднее={statistics.mean(demand):.1f}, "
          f"P80={ordered[int(0.80*SIMULATIONS)]}, "
          f"P90={ordered[int(0.90*SIMULATIONS)]}, "
          f"P95={ordered[int(0.95*SIMULATIONS)]}")
    print("\nБуфер/итер | P(пробой итерации) | P(пробой инкремента)")
    print("-" * 58)
    for b in CANDIDATE_BUFFERS:
        p_iter = probability_of_iteration_breach(b, demand)
        # инкремент пробит, если ХОТЯ БЫ одна из итераций превысила буфер
        # (буфер не копится между итерациями — правило [05])
        p_incr = 1 - (1 - p_iter) ** ITERATIONS_PER_INCREMENT
        zone = "🔴" if p_iter > 0.30 else "🟡" if p_iter > 0.10 else "🟢"
        print(f"   {b:>3} SP  |     {p_iter*100:5.1f}%  {zone}      |      {p_incr*100:5.1f}%")
```

### Как читать результат

Фактический вывод скрипта на приведённых выше входных данных (200 000 розыгрышей):

```
Спрос на буфер за итерацию (SP): среднее=13.0, P80=21, P90=28, P95=32

Буфер/итер | P(пробой итерации) | P(пробой инкремента)
----------------------------------------------------------
     8 SP  |      58.3%  🔴      |       97.0%
    12 SP  |      46.6%  🔴      |       91.8%
    16 SP  |      32.0%  🔴      |       78.6%
    20 SP  |      22.9%  🟡      |       64.6%
    24 SP  |      14.4%  🟡      |       46.3%
    30 SP  |       6.8%  🟢      |       24.4%
    36 SP  |       2.6%  🟢      |       10.0%
```

Три вывода, которые здесь важнее самих чисел:

1. **Средний спрос ≠ достаточный буфер.** Средний спрос на этих данных — 13 SP за итерацию (в среднем 2.7 вброса × 4.8 SP ≈ 13). Буфер «по среднему» (12–13 SP) пробивается почти в **каждой второй итерации** и практически гарантированно хотя бы раз за инкремент (92%).
2. **Смотрите на две вероятности отдельно.** Пробой *итерации* — рабочая ситуация, разбираемая на CCB. Пробой *инкремента* — то, что угрожает вехе. Инкремент из 4 итераций пробивается гораздо чаще отдельной итерации: даже при 6.8% на итерацию инкремент пробивается в 24% случаев. Это математика, а не пессимизм: чем больше итераций, тем выше шанс, что хотя бы одна не выдержит.
3. **Цена «зелёной зоны» на этих данных высока.** Чтобы держать пробой инкремента около 10%, нужен буфер 36 SP — это заметная доля ёмкости. Такой результат — не приговор, а сигнал: поток вбросов слишком велик и рваный для нормального буфера, и правильный ответ — не только раздувать буфер, но и работать с источником потока (дисциплина куратора, качество ТЗ) либо официально сокращать контрактный объём инкремента.

> **Не переносите эти цифры на свой проект.** Они получены на демонстрационных данных из скрипта выше. Прогоните расчёт на своей истории — результат может отличаться в разы.

> **Экономическая точка равновесия.** Наращивать буфер до 0% риска не нужно — это заморозка ёмкости. Оптимум там, где стоимость увеличения буфера (недополученная контрактная работа) сравнивается с ожидаемой ценой срыва (неустойка × вероятность). Свяжите с ценой срыва вехи из [11](11_УПРАВЛЕНИЕ_РИСКАМИ.md): `ожидаемые потери = вероятность пробоя × сумма неустойки`. Выбирайте буфер, минимизирующий сумму «замороженная ёмкость + ожидаемые потери».

### Ограничения модели (честно)

- Монте-Карло не предсказывает будущее — он экстраполирует прошлое распределение. Резкая смена поведения заказчика (новый куратор, новая фаза контракта) обнуляет историю → см. корреляционный анализ ниже.
- Нужна вменяемая история (хотя бы 8–10 итераций). На старте пользуйтесь стартовыми процентами из [05](05_ПЛАНИРОВАНИЕ_И_БУФЕРЫ.md).
- Предполагается независимость вбросов между итерациями. Если есть выраженная сезонность (валы перед приёмкой) — моделируйте её отдельно (см. ниже про стадию контракта).

## Корреляционный анализ: что влияет на интенсивность потока

Средний поток и его разброс — не константы. Они меняются в зависимости от факторов. Понимание этих зависимостей позволяет **предсказывать** рост потока, а не только реагировать постфактум.

### Факторы, которые стоит отслеживать

| Фактор | Гипотеза влияния на поток вбросов | Как использовать |
|--------|-----------------------------------|------------------|
| **Стадия контракта** | Всплеск перед приёмкой вехи (заказчик «вспоминает» требования) и в начале нового этапа | Заранее увеличивать буфер к приёмке |
| **Тип заказчика** | «Зрелый» куратор с чётким ТЗ даёт ровный поток; «размытый» многоголовый заказчик — рваный и обильный | Стартовый буфер выбирать по типу (таблица ниже) |
| **Число активных стейкхолдеров** | Больше вовлечённых лиц → выше поток (даже через одного куратора) | Мониторить как ранний индикатор |
| **Близость внешнего дедлайна регулятора** | Изменения в законе/регламенте порождают волну «внешних требований» | Резервировать дополнительный буфер под известные регуляторные даты |
| **Зрелость требований на входе** | Слабое ТЗ → поток «уточнений», часть из которых — скрытая новая функция | Усилить детектор подмены ([04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md)) |

### Профиль заказчика по потоку вбросов (стартовая типология)

Пока нет своей статистики, стартовый буфер выбирается по профилю заказчика. Шкала — **та же, что в [05](05_ПЛАНИРОВАНИЕ_И_БУФЕРЫ.md)**, здесь добавлен лишь приоритет мониторинга:

| Профиль | Признаки | Стартовый буфер вбросов | Приоритет мониторинга |
|---------|----------|-------------------------|-----------------------|
| **Стабильный** | Один зрелый куратор, детальное ТЗ, редкие изменения | 15% | Обычный |
| **Типовой** | Обычная госдинамика, умеренный поток | 20% | Обычный |
| **Турбулентный** | Много стейкхолдеров, размытое ТЗ, частые «горящие» вбросы | 25% | Повышенный + ранняя работа с куратором |

> Если расчёты этого раздела показывают, что турбулентному заказчику нужно **больше 25%** ёмкости, — это выход за рабочий диапазон методологии и повод для разговора об объёме на CCB, а не тихое увеличение буфера ([05](05_ПЛАНИРОВАНИЕ_И_БУФЕРЫ.md)). Цифры перцентиля/Монте-Карло здесь как раз и служат аргументом в этом разговоре.

### Простой корреляционный расчёт

Для проверки гипотез не нужен сложный аппарат — достаточно коэффициента корреляции Пирсона между фактором и объёмом вбросов по итерациям:

```python
import statistics

def pearson(xs, ys):
    """Коэффициент корреляции: от -1 до +1. |r| > 0.5 — заметная связь."""
    n = len(xs)
    mx, my = statistics.mean(xs), statistics.mean(ys)
    cov = sum((x-mx)*(y-my) for x, y in zip(xs, ys))
    sx = (sum((x-mx)**2 for x in xs))**0.5
    sy = (sum((y-my)**2 for y in ys))**0.5
    return cov / (sx*sy) if sx and sy else 0.0

# Пример: связь "дней до приёмки вехи" и "объёма вбросов в итерации"
days_to_acceptance = [40, 32, 24, 16, 8, 2]     # чем меньше — тем ближе приёмка
inflow_sp          = [6,  8,  10, 14, 22, 30]    # вбросы растут к приёмке
r = pearson(days_to_acceptance, inflow_sp)
print(f"r = {r:.2f}")  # сильная отрицательная связь: ближе приёмка → больше вбросов
```

> **Интерпретация:** `r ≈ -0.9` в примере означает выраженный всплеск вбросов к приёмке. Практический вывод — заранее поднять буфер в предприёмочных итерациях (динамический буфер, см. ниже), а не держать один размер на весь инкремент.

### Осторожно с выводами

- Корреляция ≠ причинность. `|r| > 0.5` — повод для гипотезы и наблюдения, а не автоматическое правило.
- Малая выборка даёт случайные корреляции. Доверяйте закономерности, устойчивой на 2+ инкрементах.
- Фактор полезен, только если ведёт к действию (изменить буфер, усилить работу с куратором). Иначе — не отслеживайте (принцип «метрика без решения бесполезна», [07](07_МЕТРИКИ.md)).

## Динамический буфер: разный размер по фазам инкремента

Из корреляционного анализа следует практический приём: **буфер не обязан быть постоянным весь инкремент**. Если данные показывают всплеск к приёмке — распределите буфер неравномерно:

```
Инкремент 8 недель, средний буфер 20%:
Итер 1  ▓▓▓░░░░░░░  15%   (спокойная фаза)
Итер 2  ▓▓▓▓░░░░░░  18%
Итер 3  ▓▓▓▓▓░░░░░  22%
Итер 4  ▓▓▓▓▓▓▓░░░  28%   (предприёмочный всплеск)
        ────────────────
        средний по инкременту ≈ 20%, но «подушка» смещена к приёмке
```

Правила:
- Средневзвешенный буфер по инкременту остаётся в границах золотого правила `100% − буфер` ([05](05_ПЛАНИРОВАНИЕ_И_БУФЕРЫ.md)).
- Профиль распределения подтверждается данными (корреляция «стадия → поток»), а не интуицией.
- Пересматривается на ретроспективе инкремента вместе с общим размером буфера.

## Как это встраивается в ритм ГРАНИТ

| Когда | Что делаем | Кто |
|-------|-----------|-----|
| Старт проекта | Стартовый буфер по профилю заказчика (типология выше) | РП + владелец продукта |
| После 2–3 инкрементов | Перцентильный расчёт (модель 1) вместо «среднее + 5%» | Менеджер изменений |
| L4–L5, высокая цена срыва | Монте-Карло (модель 2) + привязка к неустойке | РП + аналитик |
| Ретроспектива инкремента | Пересчёт буфера, проверка корреляций, профиль динамического буфера | Команда + ведущий итерации |
| Смена куратора / фазы контракта | Сброс части статистики, возврат к стартовому профилю | РП |

> **Главное не потерять за формулами:** количественные модели уточняют **размер** буфера, но не отменяют ни один механизм ГРАНИТ. Единое окно, CCB, письменная фиксация, прозрачность влияния ([04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md)) работают одинаково при буфере, посчитанном хоть по среднему, хоть по Монте-Карло. Модель помогает **обосновать** буфер перед заказчиком цифрами — но защищает проект по-прежнему дисциплина, а не симуляция.
