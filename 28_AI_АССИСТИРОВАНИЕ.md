# AI-ассистирование в ГРАНИТ

Механизмы ГРАНИТ — регистрация, классификация, оценка влияния, приоритизация, мониторинг буфера — это рутина, которую сегодня можно частично автоматизировать с помощью ИИ (LLM, ML). Этот раздел показывает, **где** ИИ реально помогает контурам методологии, **как** встроить его безопасно и, главное, **где проходит красная линия** — что ИИ не имеет права решать за человека в госконтракте.

> **Статус раздела.** Это направление развития (прицел на версию 1.2+), а не обязательная часть ядра. ГРАНИТ полностью работоспособна без единого элемента ИИ. Всё ниже — **усилители рутины**, снимающие нагрузку с менеджера изменений и РП, но не заменяющие ни CCB, ни куратора, ни письменную фиксацию.

---

## Главный принцип: ИИ ассистирует, человек решает

В госконтракте цена ошибки — неустойка и юридические последствия. Поэтому:

> **ИИ готовит и предлагает — CCB и уполномоченные люди решают и подписывают.** Ни одно контрактно-значимое решение (маршрут вброса, изменение объёма, приёмка) не принимается ИИ автоматически. ИИ ускоряет подготовку, но ответственность и подпись — всегда за человеком (принципы 4 и 9, [01](01_ПРИНЦИПЫ.md)).

Это прямое продолжение логики методологии: как один менеджер не решает судьбу вброса единолично (её решает CCB), так и ИИ не решает — он лишь ускоряет шаги 1–3 воронки ([04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md)), оставляя шаг 4 (решение) людям.

```
Воронка изменений с ИИ-ассистированием:

1. РЕГИСТРАЦИЯ    → ИИ: черновая карточка из текста заявки
2. КЛАССИФИКАЦИЯ  → ИИ: предложение типа/критичности + флаг подмены
3. ОЦЕНКА ВЛИЯНИЯ → ИИ: черновая карточка влияния по аналогам
4. РЕШЕНИЕ CCB    → ❌ ТОЛЬКО ЛЮДИ. ИИ не участвует в решении.
```

## Сценарий 1. Автоклассификация вбросов (NLP)

Самый зрелый и полезный сценарий. Заказчик пишет заявку свободным текстом — ИИ предлагает классификацию по схеме [04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md).

### Что делает ИИ

На вход — текст вброса (из письма, формы «Запроса на изменение»). На выход — **предложение** (не решение):
- **Тип:** уточнение / новая функция / дефект / внешнее требование.
- **Критичность:** P1 / P2 / P3 (по формулировкам срочности).
- **Связь с объёмом контракта:** внутри / сверх / под вопросом — сопоставлением с текстом ТЗ.
- **Флаг детектора подмены:** «заявлено как уточнение, но по признакам похоже на новую функцию» ([04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md), детектор подмены классификации).

### Почему это ценно именно для ГРАНИТ

Детектор подмены классификации — механизм, где ИИ силён: сопоставление текста заявки с ТЗ и историей на предмет «это правда уточнение или протаскивают новую функцию» — ровно задача семантического анализа. ИИ читает ТЗ целиком и не устаёт, в отличие от менеджера изменений под потоком вбросов.

### Красная линия

- ИИ **предлагает** классификацию — менеджер изменений **подтверждает или меняет**. Классификацию по-прежнему определяет суть, оценённая человеком ([04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md)).
- Особенно строго с флагом «сверх объёма»: решение о допсоглашении — контрактное, ИИ его только подсвечивает.

### Референс-подход

```
Промпт-каркас (упрощённо):
  Контекст: [релевантные пункты ТЗ + определения типов из раздела 04]
  Вход: [текст заявки заказчика]
  Задача: предложи тип, критичность, связь с объёмом; если тип "уточнение/дефект",
          но есть признаки новой логики или трудозатрат — подними флаг подмены.
  Формат: структурированный JSON + краткое обоснование со ссылкой на пункт ТЗ.
  Ограничение: это ПРЕДЛОЖЕНИЕ для менеджера изменений, не окончательное решение.
```

> Обоснование со ссылкой на пункт ТЗ обязательно — человек должен видеть, **почему** ИИ так классифицировал, чтобы проверить, а не слепо принять.

## Сценарий 2. Предиктивный fever chart (прогноз зоны буфера)

Зонный мониторинг буфера ([05](05_ПЛАНИРОВАНИЕ_И_БУФЕРЫ.md), [07](07_МЕТРИКИ.md)) показывает **текущую** зону. ИИ/ML добавляет **прогноз**: куда идёт тренд расхода буфера относительно готовности вехи.

### Что делает

На основе исторического расхода буфера, текущего темпа поступления вбросов и % готовности вехи модель прогнозирует:
- вероятную зону буфера к концу инкремента;
- ожидаемую дату пробоя буфера при сохранении тренда;
- раннее предупреждение: «при текущем темпе буфер уйдёт в 🔴 через 1.5 итерации».

Это усиливает ключевую идею [05](05_ПЛАНИРОВАНИЕ_И_БУФЕРЫ.md): смотреть **тренд** расхода, а не текущую точку. ИИ делает тренд количественным прогнозом.

### Связь с количественными моделями

Технически это продолжение Монте-Карло из [24_КОЛИЧЕСТВЕННЫЕ_МОДЕЛИ_БУФЕРОВ](24_КОЛИЧЕСТВЕННЫЕ_МОДЕЛИ_БУФЕРОВ.md), но онлайн: симуляция «доиграть инкремент» из текущей точки с учётом уже израсходованного буфера.

### Красная линия

- Прогноз — **сигнал раннего предупреждения** для CCB, не автоматическое действие. Решение (пересмотр объёма, допсоглашение) принимает CCB ([04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md)).
- Прогноз честно показывает неопределённость (доверительный интервал), а не одну «магическую» дату.

## Сценарий 3. Генерация карточек влияния по аналогам

Карточка влияния ([04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md), шаг 3) — трудоёмкая: оценка трудозатрат, что подвинется, влияние на вехи. ИИ готовит **черновик** на основе исторических аналогов из реестра изменений.

### Что делает

- Находит похожие прошлые вбросы в реестре изменений (семантический поиск).
- Предлагает оценку трудозатрат по аналогам: «похожие задачи заняли 5–8 SP».
- Черновой список «что подвинется» на основе текущего плана итерации.
- Предварительный расчёт приоритета (упрощённый WSJF) по трём факторам.

### Красная линия

- **Оценку трудозатрат подтверждает команда**, а не ИИ. Честная оценка команды — основа карточки влияния ([05](05_ПЛАНИРОВАНИЕ_И_БУФЕРЫ.md)), её нельзя отдать модели: команда учитывает контекст, которого нет в истории.
- ИИ-оценка — стартовая точка для обсуждения, ускоряющая подготовку, а не замена экспертной оценки.

## Сценарий 4. Ассистент документации и протоколов

ИИ помогает с рутиной документооборота (принцип 8 — минимум ручной бюрократии):

| Задача | Что делает ИИ | Красная линия |
|--------|---------------|---------------|
| Черновик протокола CCB | Структурирует обсуждение в шаблон протокола | Подпись куратора — только человек |
| Черновик письма-подтверждения | Формулирует по итогам созвона ([20](20_РИТУАЛЫ_ОБЩЕНИЯ/06_ШАБЛОНЫ_ПИСЕМ.md)) | Отправляет человек, проверив факты |
| Сводка реестра изменений для заказчика | Готовит дайджест потока вбросов | РП проверяет цифры перед показом |
| Трассировка ТЗ → реализация | Сопоставляет пункты ТЗ с задачами | Финальная матрица требований — за архитектором |
| Черновик карточки риска | Предлагает формулировку, категорию, меры по аналогам ([11](11_УПРАВЛЕНИЕ_РИСКАМИ.md)) | Владелец риска и триггер — назначает человек |

## Сценарий 5. Помощник дежурного по вбросам (чат-ассистент)

ИИ-бот в канале команды перенаправляет вбросы в Единое окно — автоматизирует «скрипт вежливого перенаправления» ([04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md), [20](20_РИТУАЛЫ_ОБЩЕНИЯ/03_СКРИПТЫ_РАЗГОВОРОВ.md)):

- Замечает в чате сообщение, похожее на постановку задачи.
- Вежливо предлагает оформить через Единое окно, даёт ссылку на форму.
- Помогает автору заполнить черновик заявки прямо из переписки.

Особенно ценно для распределённых команд ([27](27_РАСПРЕДЕЛЁННЫЕ_КОМАНДЫ.md)), где «невидимый вброс в личку» — главный риск. ИИ-бот повышает **дисциплину входа** ([26](26_ЗДОРОВЬЕ_МЕТОДОЛОГИИ.md)) без давления на людей.

> Красная линия: бот **перенаправляет и помогает оформить**, но не берёт задачу в работу и не классифицирует её как принятую. Он охраняет вход в воронку, а не подменяет CCB.

## Что ИИ НЕ должен делать (красные линии свода)

Единый список запретов — граница между ассистированием и недопустимой автоматизацией в госконтракте:

| ❌ ИИ не должен | Почему | Кто решает |
|-----------------|--------|-----------|
| Принимать решение о маршруте вброса | Контрактно-значимо, требует коллегиальности | CCB ([04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md)) |
| Инициировать/подписывать допсоглашение | Юридическое действие | РП + заказчик |
| Утверждать классификацию «сверх объёма» | Влияет на контракт и деньги | Менеджер изменений + CCB |
| Давать финальную оценку трудозатрат | Основа карточки влияния, нужен контекст команды | Команда |
| Принимать результат (приёмка) | Контрактный акт | Куратор заказчика ([13](13_ИНИЦИАЦИЯ_И_ПРИЁМКА.md)) |
| Подписывать протокол CCB | Юридическая защита | Куратор заказчика |
| Автоматически двигать сроки вех | Нарушает контрактную чистоту (принцип 1) | Только допсоглашение |
| Оценивать людей (velocity как KPI) | Убивает честность данных ([07](07_МЕТРИКИ.md), [26](26_ЗДОРОВЬЕ_МЕТОДОЛОГИИ.md)) | Не делается вообще |

## Риски ИИ-ассистирования

Дополнение к каталогу рисков ([11](11_УПРАВЛЕНИЕ_РИСКАМИ.md)):

| Риск | Проявление | Мера |
|------|-----------|------|
| **Слепое доверие ИИ** | Человек принимает предложение ИИ не глядя | Обязательное обоснование от ИИ + подтверждение человеком; аудит расхождений |
| **Галлюцинации** | ИИ выдумывает оценку/классификацию | Требовать ссылки на источник (пункт ТЗ, аналог); проверка человеком |
| **ИБ и данные контракта** | Данные ТЗ/заказчика уходят во внешний ИИ-сервис | Только on-premise/доверенные модели; ИБ-ревень ([10](10_КАЧЕСТВО_И_DOD.md)); запрет облачных LLM для чувствительных данных |
| **Импортозамещение** | Иностранный ИИ-сервис не проходит требования | Отечественные/локальные модели ([15](15_ИМПОРТОЗАМЕЩЕНИЕ.md)) |
| **Смещение в исторических данных** | ИИ повторяет прошлые ошибки оценки | Периодическая калибровка на факте, человек в контуре |
| **Эрозия компетенций** | Команда разучивается классифицировать/оценивать сама | ИИ как ассистент, а не костыль; ротация ручной работы |

> **ИБ и импортозамещение — критичны.** Данные госконтракта (ТЗ, переписка с заказчиком) часто чувствительны. Использование ИИ проходит то же ИБ-ревью, что любой модуль ([10](10_КАЧЕСТВО_И_DOD.md)), и те же требования реестрового ПО ([15](15_ИМПОРТОЗАМЕЩЕНИЕ.md)). Облачные иностранные LLM для данных контракта, как правило, недопустимы — используйте локально развёрнутые или отечественные модели.

## Уровни внедрения ИИ (по зрелости)

ИИ подключается **после** того, как процесс работает вручную — не раньше (иначе автоматизируется хаос):

| Уровень зрелости ([19](19_МОДЕЛЬ_ЗРЕЛОСТИ.md)) | Уместное ИИ-ассистирование |
|-----------------------------------------------|----------------------------|
| L1–L2 | **Никакого.** Сначала пусть заработает Единое окно и CCB вручную |
| L3 | Ассистент документации (черновики протоколов, писем), чат-бот перенаправления |
| L4 | Автоклассификация (предложения), генерация карточек влияния по аналогам |
| L5 | Предиктивный fever chart, полный ассистент рутины с калибровкой на данных |

> Правило то же, что для инструментария ([23](23_ИНСТРУМЕНТАРИЙ.md)): не прыгайте в ИИ-автоматизацию, пока не заработал ручной процесс. ИИ усиливает работающую дисциплину, но не создаёт её.
