# Распределённые и удалённые команды

Ядро ГРАНИТ и раздел [16_СУБПОДРЯДЧИКИ](16_СУБПОДРЯДЧИКИ.md) неявно предполагают, что команда работает в общем ритме и может собраться на CCB, планирование, ежедневку. Но всё чаще госконтракты исполняются **распределёнными командами**: часть в офисе, часть удалённо, субподрядчик в другом городе и часовом поясе, аналитик у заказчика на площадке. Распределённость не меняет механизмы ГРАНИТ, но меняет **как** их исполнять — иначе Единое окно, CCB и ритуалы общения незаметно ломаются. Этот раздел адаптирует церемонии, коммуникации и контроль под распределённый формат.

> **Когда это нужно.** Если команда сидит в одной комнате — раздел не нужен. Он включается, когда: (а) есть постоянно удалённые участники, (б) команда в разных часовых поясах, (в) субподрядчик работает с другой площадки, (г) куратор заказчика физически далеко и не может прийти на очный CCB.

---

## Принцип: распределённость усиливает вбросы, а не ослабляет

Ключевое наблюдение: **удалёнка не снижает поток вбросов — она делает его менее видимым.** В офисе вброс «в коридоре» хотя бы слышен коллегам; удалённо он уходит в личку разработчику и не всплывает нигде. Поэтому для распределённой команды дисциплина Единого окна не менее, а **более** критична.

```
Офис:      вброс в коридоре → слышат соседи → есть шанс перенаправить в окно
Удалёнка:  вброс в личку/чат → не видит никто → тихо взят в работу → срыв
```

Вывод: чем распределённее команда, тем строже правило «нет регистрации — нет задачи» ([01](01_ПРИНЦИПЫ.md), принцип 2) и тем важнее асинхронная письменная фиксация всего.

## Адаптация церемоний под распределённый формат

| Церемония | Офисная норма | Распределённая адаптация |
|-----------|---------------|--------------------------|
| **Ежедневная синхронизация** | 15 мин устно | Гибрид: короткий видеозвонок **или** асинхронный текстовый стендап в канале (что сделано / план / препятствия / буфер) — по часовым поясам. Видео обязательно ≥ 1 раза в неделю для «сверки лиц». |
| **Планирование итерации** | Очно у доски | Видео + общая онлайн-доска (экран у всех). Обязательно включённые камеры — оценка требует вовлечённости. |
| **Планирование инкремента** | 1–2 дня очно | По возможности **очно хотя бы раз** (kickoff инкремента). Если невозможно — разбить на несколько коротких сессий вместо одного марафона (усталость от видео выше). |
| **CCB** | Очно с куратором | Видео обязательно (не телефон, не переписка): решения по объёму требуют видеть реакцию куратора. Протокол — сразу в общий документ на экране. |
| **Демо** | Очный показ | Запись демо + живая сессия. Запись критична: заказчик со стороны часто не может прийти, но должен видеть результат (снижает вбросы «я не видел, переделайте»). |
| **Ретроспектива** | Очно, откровенно | Видео + анонимный сбор проблем заранее (удалённо люди менее откровенны вслух). Инструмент анонимного ввода обязателен. |
| **Гейт соответствия** | Очная проверка | Чек-лист в общем документе, ответственные отмечаются асинхронно, финальное решение — на видео. |

### Правило «двух каналов» для распределённого CCB

CCB — самая уязвимая церемония при распределённости, потому что от неё зависит юридическая защита. Правило:

> Распределённый CCB ведётся **в двух каналах одновременно**: видеосвязь (обсуждение, реакция куратора) + общий документ-протокол, заполняемый в реальном времени на экране. Решение считается принятым, только когда оно **записано в документе и подтверждено куратором в кадре**. «Кивнул в зуме» без записи = решение не принято (принцип 4).

## Асинхронность как первый класс

В распределённой команде (особенно в разных часовых поясах) не всё можно решить синхронно. ГРАНИТ адаптируется через явное разделение: что требует синхрона, а что живёт асинхронно.

| Требует синхрона (видео) | Живёт асинхронно (текст/документ) |
|--------------------------|-----------------------------------|
| Решения CCB по объёму | Регистрация вброса в Едином окне |
| Планирование инкремента (kickoff) | Классификация и оценка влияния вброса |
| Разбор конфликта/плохих новостей ([20](20_РИТУАЛЫ_ОБЩЕНИЯ/04_РИТУАЛ_ПЛОХИХ_НОВОСТЕЙ.md)) | Обновление реестра изменений, статусов |
| Ретроспектива (обсуждение) | Сбор проблем к ретро, метрики |
| Оценка сложных задач командой | Ежедневный стендап (текстом по поясам) |

### Правило асинхронного вброса

Единое окно в распределённой команде работает **полностью асинхронно** — и это его сила:

- Вброс регистрируется в трекере в любое время из любого пояса (форма создания «Запроса на изменение», [23](23_ИНСТРУМЕНТАРИЙ.md)).
- Классификация и карточка влияния готовятся асинхронно менеджером изменений.
- На синхронный CCB выносится **уже подготовленное** решение — экономит дефицитное общее время в кадре.

> Асинхронное окно + синхронный CCB — оптимальное разделение: рутина (регистрация, оценка) не ждёт общего времени, а дефицитный синхрон тратится только на то, что действительно требует живого обсуждения (решения по объёму).

## Часовые пояса: окно пересечения

Когда команда в разных поясах, критичен **общий рабочий интервал** (когда все онлайн одновременно).

```
Москва     09 ─────────────── 18
Омск (+3)     12 ─────────────── 21
Владивосток   ... почти нет пересечения с Москвой
              ▲──────────▲
           окно пересечения (напр. 12:00–15:00 МСК)
```

Правила:
- Все синхронные церемонии (CCB, ежедневка-видео) — **только в окне пересечения**.
- Окно пересечения священно: не занимать его индивидуальной работой.
- Если пересечения почти нет (>6 часов разницы) — переходить на «следуй за солнцем»: асинхронная передача работы, синхрон только для CCB по предварительной записи.
- Буфер интеграции для распределённого субподряда ([16](16_СУБПОДРЯДЧИКИ.md)) увеличивается: разница поясов замедляет согласования.

## Коммуникации и ритуалы удалённо

Раздел [20_РИТУАЛЫ_ОБЩЕНИЯ](20_РИТУАЛЫ_ОБЩЕНИЯ/README.md) держится на регулярности и предсказуемости. Удалённо это ещё важнее, но исполняется иначе:

- **Регулярность важнее формата.** Еженедельный статус в одно и то же время (даже текстом) держит ритм и доверие лучше, чем нерегулярные подробные созвоны.
- **Плохие новости — всё равно голосом/видео.** Ритуал плохих новостей ([20](20_РИТУАЛЫ_ОБЩЕНИЯ/04_РИТУАЛ_ПЛОХИХ_НОВОСТЕЙ.md)) удалённо нельзя переводить в переписку: риск срыва озвучивается на видео, не в чате (текст холоден и провоцирует эскалацию).
- **Реестр изменений на экране — сильнее вживую.** Демонстрация потока вбросов через шеринг экрана на видео-CCB работает так же отрезвляюще, как очно: «вы принесли 15 задач за месяц».
- **Письмо-подтверждение обязательно после любого созвона.** Удалённо «решено устно» ещё опаснее — нет даже свидетелей в комнате. Нет письма — нет решения ([20](20_РИТУАЛЫ_ОБЩЕНИЯ/README.md), золотое правило 3).

## Специфика распределённого субподряда

Дополняет [16_СУБПОДРЯДЧИКИ](16_СУБПОДРЯДЧИКИ.md) с учётом распределённости:

- **Субподрядчик — «чёрный ящик» вдвойне.** Удалённый субподряд ещё труднее контролировать. Противоядие: промежуточные статусы **чаще** (не реже раза в неделю на видео) и общий доступ к трекеру, а не отчёты по почте.
- **Общий трекер, а не пересылка задач.** Субподрядчик работает в вашей Jira/трекере (гостевой доступ к своему компоненту), чтобы статусы были видны в реальном времени, а не приходили выгрузками. Это снимает информационный лаг распределённости.
- **Буфер интеграции с запасом на пояса и согласования.** К обычному буферу интеграции добавляется запас на замедление коммуникации через границы организаций и поясов.
- **ИБ удалённого доступа.** Гостевой доступ субподрядчика к трекеру/среде — предмет ИБ-ревью ([10](10_КАЧЕСТВО_И_DOD.md), DoD): VPN, ограничение прав компонентом, аудит доступа.

## Риски распределённых команд

Дополнение к каталогу рисков ([11](11_УПРАВЛЕНИЕ_РИСКАМИ.md)):

| Риск | Проявление | Мера |
|------|-----------|------|
| **Невидимый вброс** | Задача взята в личке, не прошла окно | Строгая дисциплина окна, аудит задач без записи в реестре ([26](26_ЗДОРОВЬЕ_МЕТОДОЛОГИИ.md), дисциплина входа) |
| **Эрозия ежедневного ритма** | Стендапы «плывут», пропускаются | Фиксированное окно пересечения, асинхронный формат для дальних поясов |
| **Изоляция и выгорание** | Удалённый участник «выпадает», перегруз незаметен | Индекс перегрузки ([07](07_МЕТРИКИ.md)) + регулярные 1:1, видео ≥ раза в неделю |
| **Bus factor усиливается** | Удалённый «герой» ещё менее заметен | Общий трекер, документирование, парная работа онлайн ([14](14_ЗНАНИЯ_И_КОМАНДА.md)) |
| **Лаг согласований** | Решения ждут окна пересечения поясов | Асинхронное окно + чёткое разделение sync/async |
| **Разрыв контекста** | Удалённые не знают «кулуарных» договорённостей | Всё письменно в общем пространстве, запрет «решений в личке» |

## Инструментализация (усиление раздела 23)

Для распределённой команды инструмент из [23_ИНСТРУМЕНТАРИЙ](23_ИНСТРУМЕНТАРИЙ.md) — не удобство, а **основной канал синхронизации** (заменяет офисную «видимость»):

- **Единое окно только в трекере** (не в чатах): единственный источник правды о вбросах, доступный всем поясам асинхронно.
- **Доска онлайн у всех** на планировании и ежедневке (шеринг экрана или общий доступ).
- **Дашборд здоровья** ([07](07_МЕТРИКИ.md)) — общедоступен, заменяет «взгляд через плечо».
- **Автоматические напоминания** ([23](23_ИНСТРУМЕНТАРИЙ.md), ScriptRunner): просроченные вбросы, зависшие задачи — критичны, когда нет офисного «а что там с задачей X».
- **Запись демо и ключевых решений** — асинхронный доступ для тех, кто был вне окна пересечения.

## Чек-лист готовности распределённой команды

- [ ] Определено окно пересечения часовых поясов, синхронные церемонии — в нём
- [ ] Единое окно работает полностью асинхронно (регистрация из любого пояса)
- [ ] Разделено: что требует синхрона (видео), что живёт асинхронно
- [ ] CCB ведётся по правилу «двух каналов» (видео + документ-протокол)
- [ ] Демо записывается для отсутствующих
- [ ] Ежедневка адаптирована (гибрид видео/текст), видео ≥ раза в неделю
- [ ] Ретро собирает проблемы анонимно и заранее
- [ ] Субподрядчик работает в общем трекере, а не через выгрузки
- [ ] Буфер интеграции увеличен на лаг поясов и согласований
- [ ] ИБ-ревью удалённого доступа проведено
- [ ] Правило «нет письма — нет решения» соблюдается после каждого созвона
