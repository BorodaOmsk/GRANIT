# Сквозной кейс: один вброс от начала до конца

Учебный документ. Мы проведём одну внеплановую задачу заказчика через **все** механизмы ГРАНИТ — от звонка до сдачи — и на каждом шаге покажем, какой раздел методологии работает. Это «день из жизни вброса»: связный рассказ вместо разрозненных правил.

> Как читать: слева — что происходит по сюжету, во врезках `▶ Механизм` — какое правило ГРАНИТ и из какого раздела сработало. Цифры условны и служат иллюстрацией.

---

## Декорации

- **Проект:** информационная система для госзаказчика, идёт по ГРАНИТ.
- **Текущая веха:** № 3 «Модуль отчётности», контрактная дата приёмки — через 6 недель.
- **Сейчас:** идёт Итерация 2 из 4 внутри инкремента. Ёмкость итерации — 40 SP: контрактный поток 32 SP (в т.ч. резерв техдолга ~3 SP), буфер вбросов 8 SP (20%).
- **Действующие лица:** Куратор заказчика (Ирина), РП (Сергей), Менеджер изменений (он же владелец продукта, Анна), Ведущий итерации (Павел), команда.

---

## Шаг 0. Вброс прилетает «не туда»

Пятница, 16:40. Разработчику Диме пишет в личку **начальник отдела заказчика** (не Ирина):

> «Дим, привет! К отчёту по вехе 3 нужно срочно добавить выгрузку в Excel с фильтром по регионам. Это же мелочь, к понедельнику сделаешь?»

Дима мог бы начать делать. Но он работает по ГРАНИТ.

```
▶ Механизм: Единое окно (принцип 2, [04])
   Дима не берёт задачу молча. Отвечает по скрипту перенаправления:
   «Понял задачу. Чтобы корректно встроить её в план и не сорвать
   обязательства по вехе 3, зарегистрирую через менеджера изменений —
   он подготовит оценку, и примем решение по срокам.»
   ([20_РИТУАЛЫ_ОБЩЕНИЯ/03_СКРИПТЫ_РАЗГОВОРОВ])
```

```
▶ Механизм: один куратор ([02], [12])
   Запрос пришёл не от Ирины. Дима не игнорирует начальника отдела, но
   объясняет: задача пойдёт через куратора Ирину, которая сводит
   приоритеты стороны заказчика. Иначе — противоречивые указания.
```

Дима пересылает формулировку Анне (менеджеру изменений).

## Шаг 1. Регистрация

Анна заносит вброс в **реестр изменений**:

| Поле | Значение |
|------|----------|
| ID | CH-047 |
| Дата | пятница |
| Автор (через куратора) | Начальник отдела → подтвердит Ирина |
| Суть | Выгрузка отчёта в Excel с фильтром по регионам |
| Заявленная срочность | «к понедельнику» |
| Статус | Новый |

```
▶ Механизм: Реестр изменений — источник правды ([04], шаблон [09])
   Нет записи — нет задачи. Теперь вброс существует официально, виден и
   не потеряется. Заодно он пополнит статистику для пересчёта буфера.
```

Первым делом Анна проверяет легитимность автора: связывается с Ириной. Ирина подтверждает, что запрос действительно от стороны заказчика и она берёт его в свою очередь приоритетов.

## Шаг 2. Классификация (и проверка на подмену)

Заказчик назвал это «мелочью». Анна классифицирует по сути, а не по ярлыку.

- **Тип?** Заявлено как «уточнение отчёта». Но выгрузка в Excel с фильтрацией по регионам — это **новая логика, которой нет в ТЗ вехи 3**.
- **Связь с контрактом?** В ТЗ есть отчёт на экране, выгрузки в Excel нет.

```
▶ Механизм: детектор подмены классификации ([04])
   Красный флаг: «уточнение» добавляет новую логику/поведение, которых
   нет в ТЗ. Переклассификация: это НЕ уточнение, а НОВАЯ ФУНКЦИЯ,
   объём СВЕРХ контракта. Значит — кандидат на изменение контракта.
```

- **Критичность?** Система работает, отчёт на экране есть. «К понедельнику» — это желание, а не авария. Значит **P3** (плановый вброс), не P1/P2.

```
▶ Механизм: классификация по критичности ([03])
   P3 идёт стандартным путём через еженедельный CCB, а не по fast-track.
   Ложная срочность «к понедельнику» отсечена объективным критерием.
```

## Шаг 3. Оценка влияния

Анна с командой готовят **карточку влияния** CH-047:

```
Трудозатраты:            13 SP (реалистичная)
Влезает в буфер?         Нет. В буфере осталось 5 SP из 8 (уже потратили
                         на CH-045). 13 > 5.
Что придётся подвинуть:  Чтобы взять сейчас — сдвинуть задачу «Печатные
                         формы» (9 SP) на Итерацию 3.
Сдвиг вех:               Веха 3 — риск +3 дня, если брать в текущий инкремент.
Технический риск:        Средний: нужна библиотека выгрузки, совместимая
                         с целевой платформой (проверить по реестру стека).
```

```
▶ Механизм: карточка влияния — всегда выбор, не «да/нет» ([04], [09])
   Итог оформляется как варианты для заказчика, а не приговор.
```

```
▶ Механизм: связь со стеком и ИБ ([15], [10])
   Библиотека выгрузки должна быть совместима с отечественной платформой —
   это попадёт в DoD задачи. Проверка заложена заранее, а не всплывёт на приёмке.
```

Оценка приоритета на случай конкуренции за буфер:

```
▶ Механизм: WSJF ([04])
   Ценность 4 + Срочность 2 + Снижение риска 1 = 7; / 13 SP ≈ 0,54.
   Невысокий приоритет: полезно, но не горит и дорого. В очереди буфера
   уступит более дешёвым и срочным задачам.
```

## Шаг 4. Решение на CCB

Среда, 11:00, еженедельный **CCB**. Участники: Сергей (РП, председатель), Ирина (куратор), Анна (менеджер изменений). На экране — реестр изменений и карточка CH-047.

Анна докладывает карточку. Обсуждение идёт на языке вариантов:

- **Вариант А:** взять в Итерацию 3 из буфера, сдвинув «Печатные формы» → риск вехе +3 дня.
- **Вариант Б:** в следующий инкремент, без сдвигов текущих обязательств.
- **Вариант В:** раз это объём сверх ТЗ — оформить допсоглашение (отдельная оплата + при необходимости срок).

```
▶ Механизм: решение принимает заказчик, под протокол ([04], принципы 1, 9)
   Сергей не решает за Ирину. Он показывает цену каждого варианта.
   Ирина выбирает: функция нужна, но не срочно → Вариант Б
   (следующий инкремент). Поскольку это объём сверх ТЗ — параллельно
   готовится допсоглашение об оплате доработки.
```

Оформляется **протокол CCB**:

| ID | Суть | Решение | Обоснование |
|----|------|---------|-------------|
| CH-047 | Выгрузка в Excel по регионам | Следующий инкремент + допсоглашение | Объём сверх ТЗ вехи 3; не срочно |

Протокол подписывают Сергей и Ирина.

```
▶ Механизм: защита от «замечания-трояна» ([13], [17])
   Функцию не протащили бесплатно под видом «мелочи к вехе 3».
   Веха 3 осталась в исходном объёме и сроке — она защищена.
```

## Шаг 5. Допсоглашение и попадание в план

Поскольку выбран маршрут «изменение контракта», РП инициирует **допсоглашение** (объём + оплата доработки). Пока оно готовится юридически, задача ждёт в бэклоге следующего инкремента.

```
▶ Механизм: контрактная чистота (принцип 1)
   Веха двигается/объём растёт только через официальное допсоглашение,
   а не «по договорённости». Юридическая защита обеих сторон.
```

На **планировании следующего инкремента** Анна (владелец продукта) ставит CH-047 в бэклог. Перед взятием в итерацию задача проходит входной фильтр:

```
▶ Механизм: Definition of Ready ([10])
   [✔] Зарегистрирована через Единое окно, автор подтверждён куратором
   [✔] Есть AC: «Дано отчёт на экране → когда нажата Выгрузка в Excel с
       выбранными регионами → тогда скачивается .xlsx только по этим регионам»
   [✔] Классификация и связь с объёмом определены (новая функция, допсоглашение)
   [✔] Внешние зависимости выявлены (библиотека выгрузки на целевой платформе)
   [✔] Оценена командой (13 SP)
   [✔] AC согласованы с Ириной (контрактно-значимая)
   Задача готова к взятию.
```

## Шаг 6. Исполнение под WIP-лимитом

Задача взята в итерацию. На доске действует WIP-лимит.

```
▶ Механизм: WIP-лимит ([05])
   CH-047 не начинают, пока не завершена предыдущая задача разработчика.
   Буфер защищает ёмкость от вбросов, WIP-лимит — фокус от распыления.
   Никакого «хватаемся за всё сразу».
```

Ежедневно на синхронизации Павел (ведущий итерации) отслеживает состояние буфера и прогресс.

---

## Шаг 7. Завершение: Definition of Done

Задача сделана. Прежде чем считать её готовой, проходит **DoD** — тот же, что у любой плановой задачи.

```
▶ Механизм: единый DoD, вброс не исключение ([10])
   Разработка:     [✔] код-ревью [✔] автотесты проходят [✔] стат.анализ чист
   Соответствие:   [✔] совместимо с отечественной платформой (проверена
                       библиотека выгрузки) [✔] ИБ-требования [✔] ГОСТ/ТЗ
   Документация:   [✔] эксплуатационная обновлена [✔] матрица требований
                       обновлена (новая функция трассирована к допсоглашению)
   Проверка:       [✔] функц. тестирование по AC [✔] демо владельцу продукта
   «Быстро и без документации» — не случилось. Скрытого техдолга нет.
```

## Шаг 8. Демо и приёмка

В конце итерации — **демо**. Ирина видит работающую выгрузку в Excel.

```
▶ Механизм: демо → сигналы в окно, не в работу ([06], [20])
   На демо Ирина говорит: «А можно ещё выгрузку в PDF?». Это НЕ берут
   сразу — фиксируют как новый вброс CH-052 в Единое окно.
   Цикл повторяется. Демо собирает сигналы, решения — на CCB.
```

Функция принята внутренне владельцем продукта. Поскольку она пошла по допсоглашению, её приёмка идёт по условиям этого допсоглашения (а не в составе исходной вехи 3).

## Что произошло с точки зрения методологии

За один вброс сработали почти все контуры:

| Контур | Что сделал |
|--------|-----------|
| Управления изменениями | Поймал вброс в Единое окно, классифицировал, оценил, провёл через CCB |
| Контрактный | Защитил веху 3, инициировал допсоглашение на новый объём |
| Исполнительный | Взял задачу в итерацию под DoR/WIP/DoD, показал на демо |
| Координационный | Поставил в план следующего инкремента с учётом зависимостей |
| Устойчивости | Проверил совместимость со стеком и ИБ, не породил техдолг |

**Итог:** внеплановая задача выполнена, заказчик доволен, веха 3 не сорвана, новый объём оплачен по допсоглашению, всё зафиксировано письменно. Это и есть ГРАНИТ в действии — «да, и вот на каких условиях» вместо «нет» или тихого срыва.

## Мини-версия для запоминания

```
Вброс → перенаправить в Единое окно (не брать молча)
      → зарегистрировать (нет записи — нет задачи)
      → классифицировать по сути, не по ярлыку (детектор подмены)
      → карточка влияния = варианты А/Б/В, не «да/нет»
      → CCB решает под протокол (заказчик выбирает, РП показывает цену)
      → маршрут: буфер / инкремент / допсоглашение / отклонить
      → DoR на входе → WIP при работе → DoD на выходе
      → демо (новые хотелки → снова в окно)
```

Хотите глубже по любому шагу — см. [21_БЫСТРЫЙ_СТАРТ_И_FAQ](21_БЫСТРЫЙ_СТАРТ_И_FAQ.md).
