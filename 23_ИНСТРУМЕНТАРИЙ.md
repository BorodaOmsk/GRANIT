# Инструментарий: настройка Jira под ГРАНИТ

Методология описывает *что* и *почему*. Этот раздел — про *чем*: как положить контуры ГРАНИТ на конкретный инструмент. За основу взята **Jira Server / Data Center + ScriptRunner** — связка, наиболее распространённая в контуре госзаказа (on-premise, без облака). Настройки даны подробно и готовы к переносу.

> **Важно про облако.** Инструкции ориентированы на **Jira Server / Data Center**, а не на Jira Cloud. В Cloud нет ScriptRunner-постфункций в том же виде, другой REST API и другой движок автоматизации (Automation for Jira встроен). Если у вас Cloud — идеи маппинга те же, но реализация будет отличаться.

> **Важно про импортозамещение и уход Atlassian из РФ.** Atlassian прекратил продажи и поддержку в России, новые лицензии Jira/ScriptRunner официально недоступны, обновления безопасности не поступают. Для госконтрактов с требованием реестрового ПО ([15](15_ИМПОРТОЗАМЕЩЕНИЕ.md)) Jira, как правило, **не проходит** как целевая платформа. Поэтому:
> - Раздел применим, если Jira **уже развёрнута** и легально используется (приобретена до ограничений) как внутренний рабочий инструмент команды исполнителя, не входящий в состав поставки заказчику.
> - Для новых проектов рассмотрите отечественные трекеры — маппинг контуров ГРАНИТ универсален (см. [«Отечественные аналоги»](#отечественные-аналоги-импортозамещение) в конце раздела).
>
> Иными словами: **ГРАНИТ не привязан к Jira**. Jira здесь — подробный пример реализации, а не требование методологии.

## Принцип: инструмент под методологию, а не наоборот

Прежде чем настраивать — правило, уберегающее от главной ошибки автоматизации:

> **Настраивайте ровно столько, сколько нужно контурам ГРАНИТ. Каждое поле, статус и правило должны обслуживать конкретный механизм методологии — иначе это «бюрократия ради бюрократии» ([17](17_АНТИПАТТЕРНЫ_И_КЕЙСЫ.md)), только в цифровом виде.**

Перегруженный обязательными полями workflow убивает скорость регистрации вброса — а именно скорость входа делает Единое окно работающим. Минимализм здесь — не лень, а следование принципу 8 ([01](01_ПРИНЦИПЫ.md)).

Ориентир объёма настройки по зрелости ([19](19_МОДЕЛЬ_ЗРЕЛОСТИ.md)):
- **L2 (Единое окно работает):** один проект + тип задачи «Запрос на изменение» + отдельная доска-очередь (фильтр по типу) + базовый workflow. Этого достаточно, чтобы стартовать.
- **L3 (буферы на данных):** + кастомные поля буфера/критичности, JQL-представления, первые дашборды.
- **L4–L5 (метрики и самонастройка):** + автоматизация ScriptRunner, расчёт приоритета, зонный мониторинг, эскалации.

Не прыгайте сразу в L4 — сначала пусть заработает вход.

> **Один проект, а не зоопарк проектов.** Не плодите отдельные Jira-проекты под вбросы, риски, техдолг. Всё живёт в **одном проекте команды**, а разделение потоков достигается тремя штатными средствами: **типом задачи** (что это), **метками/компонентами** (к какому потоку относится) и **доской + JQL** (как это увидеть). Отдельные проекты порождают дубли настроек, сложные связи и рассинхрон прав — это цифровой аналог бюрократии ([17](17_АНТИПАТТЕРНЫ_И_КЕЙСЫ.md)).

## Предпосылки: что должно быть установлено

Для полной реализации раздела нужны:

| Компонент | Зачем | Обязательность |
|-----------|-------|----------------|
| **Jira Software Server / Data Center** | Базовая платформа: проекты, доски, workflow, дашборды, JQL | Обязательно |
| **ScriptRunner for Jira** (Adaptavist) | Постфункции, слушатели, валидаторы, scripted-поля, запланированные задания, JQL-функции — вся автоматизация ниже написана под него | **Обязательно для разделов «Автоматизация» и части полей.** Без него доступен только базовый функционал (штатные постфункции, ручной расчёт) |
| Права администратора Jira | Создание типов задач, полей, схем, workflow | Обязательно на этапе настройки |

> **Все скрипты ниже предполагают установленный и работающий ScriptRunner for Jira** (совместимой с вашей версией Jira редакции). Если ScriptRunner не установлен — автоматические расчёты (приоритет, расход буфера, зоны, эскалации) выполняются вручную или заменяются штатными средствами Jira с потерей гибкости. Установка: через **Manage apps** (UPM) или из файла .obr/.jar, при отсутствии доступа к Marketplace — оффлайн-установкой совместимой версии.

> ⚠️ Скрипты приведены как **референс-реализация** и требуют адаптации: ID полей (`customfield_XXXXX`), имена статусов и переходов, ключ проекта и названия меток в вашей инсталляции будут другими. Проверяйте на тестовом стенде перед продом ([10](10_КАЧЕСТВО_И_DOD.md): совместимость и ИБ-ревью — часть DoD и для служебной автоматизации).

| **Приоритет (упрощённый WSJF)** | 3 числовых поля + scripted-поле результата | Расчёт автоматизируется |
| **Решение CCB / маршрут** | Статус workflow + поле «Маршрут» | Буфер/Инкремент/Допсоглашение/Отклонено |
| **Протокол CCB** | Комментарий/поле решения + приложение подписанного протокола | Подпись остаётся вне Jira (юр. документ) |
| **Контрактная задача** | Тип «История»/«Задача» + метка `контракт` (или её отсутствие метки `вброс`) | Контрактный поток в том же проекте |
| **Веха** | **Версия (Version / fixVersion)** или Epic | Дата версии = контрактная дата приёмки |
| **Инкремент** | **Спринт-контейнер** / метка / представление доски | 8–10 недель |
| **Итерация** | **Спринт** (2 недели) | Штатный Sprint |
| **Буфер вбросов** | Метка `вброс` на задачах + гаджет расхода по SP | Считается по SP задач с меткой `вброс` в спринте |

| **Реестр техдолга** ([05](05_ПЛАНИРОВАНИЕ_И_БУФЕРЫ.md)) | Тип задачи **«Техдолг»** + метка `техдолг` | Отслеживается фильтром, не отдельным проектом |
| **DoR / DoD** ([10](10_КАЧЕСТВО_И_DOD.md)) | Чек-лист (ScriptRunner Behaviours / поле-чеклист) + валидаторы перехода | Контроль на входе и выходе |
| **Панель здоровья** ([07](07_МЕТРИКИ.md)) | Дашборд с гаджетами | См. ниже |

## Схема одного проекта: доски, типы, метки

Всё — в **одном проекте команды**. Отдельные проекты не заводим. Разделение «контрактный поток / поток вбросов / риски / техдолг» ([README](README.md)) достигается тремя штатными механизмами Jira.

**1. Тип задачи — отвечает на вопрос «что это».**

| Тип задачи | Поток | Назначение |
|------------|-------|-----------|
| История / Задача | Контрактный | Плановая работа по вехам |
| **Запрос на изменение** | Вбросы | Входящий вброс, идёт по воронке CCB |
| Дефект | Качество (вне буфера) | Несоответствие принятому ([04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md)) |
| Техдолг | Резерв техдолга | Погашение долга ([05](05_ПЛАНИРОВАНИЕ_И_БУФЕРЫ.md)) |
| Риск | Реестр рисков | Риски с владельцем и триггером ([11](11_УПРАВЛЕНИЕ_РИСКАМИ.md)) |

**2. Метка (label) — отвечает на вопрос «к какому потоку относится».**
- `вброс` — задача, взятая в работу из одобренного вброса (для подсчёта расхода буфера).
- `техдолг`, `риск` — дублируют тип для удобных быстрых фильтров, если нужно.
- Метки — самый дешёвый механизм; не требуют администрирования схем.

**3. Доски (Agile boards) — отвечают на вопрос «как это увидеть».** Несколько досок поверх **одного** проекта, каждая со своим JQL-фильтром:

```
                     ОДИН ПРОЕКТ (напр. ключ GRN)
   ┌───────────────────────────────────────────────────────────────┐
   │  Задачи всех типов: История, Запрос на изменение, Дефект,       │
   │  Техдолг, Риск — различаются типом, метками, версией (вехой)    │
   └───────────────────────────────────────────────────────────────┘
        ▲                        ▲                         ▲
        │ доска-фильтр           │ доска-фильтр            │ доска-фильтр
   ┌────┴─────────┐      ┌───────┴────────┐        ┌───────┴─────────┐
   │ ДОСКА        │      │ ДОСКА          │        │ ДОСКА           │
   │ «Единое окно»│      │ «Разработка»   │        │ «Риски»         │
   │ Kanban       │      │ Scrum, спринты │        │ (по типу Риск)  │
   │ issuetype =  │      │ issuetype in   │        │ issuetype = Риск│
   │ "Запрос на   │      │ (История,Задача│        │                 │
   │  изменение"  │      │ ,Дефект,Техдолг)│       │                 │
   └──────────────┘      └────────────────┘        └─────────────────┘
     воронка CCB           контрактный поток          мониторинг рисков
                           + буфер (метка «вброс»)
```

- **Доска «Единое окно»** (Kanban) — колонки = статусы воронки CCB (Новый → Классификация → Оценка → На CCB → маршрут). Фильтр: `issuetype = "Запрос на изменение"`.
- **Доска «Разработка»** (Scrum) — контрактный поток и принятые вбросы, спринты = итерации, версии = вехи. Быстрый фильтр «Только вбросы» (`labels = вброс`) для визуального контроля расхода буфера.
- **Доска «Риски»** (по желанию) — тип «Риск».

> **Почему не отдельные проекты.** Один проект = единые схемы полей, статусов, прав и одно место для отчётов. Вбросы не «шумят» в контрактной работе не потому, что лежат в другом проекте, а потому что у них **свой тип, своя доска и свой JQL**. Это ровно то разделение, что нужно методологии, — без накладных расходов на второй проект и связи-переносы между ними.

**Одобренный вброс не переносится между проектами** — он просто меняет статус на своей доске и получает метку `вброс` + попадает в спринт на доске «Разработка» (обе доски смотрят в один проект, поэтому «перенос» не нужен).

**Несколько команд:** один проект на команду со своими досками, либо один общий проект с досками по компонентам/меткам команд. CCB и реестр изменений остаются едиными (общий фильтр по типу «Запрос на изменение» через все команды).

## Кастомные поля

Минимально достаточный набор под карточку влияния и приоритизацию. Названия — примерные, ID (`customfield_XXXXX`) у вас будут свои.

| Поле | Тип | Значения / формат | Обслуживает механизм |
|------|-----|-------------------|----------------------|
| **Тип вброса** | Select (одиночный) | Уточнение / Новая функция / Дефект / Внешнее требование | Классификация, детектор подмены ([04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md)) |
| **Критичность** | Select | P1 / P2 / P3 | Fast-track ([03](03_ЖИЗНЕННЫЙ_ЦИКЛ.md)) |
| **В объёме контракта** | Select | Да / Нет / Под вопросом | Маршрут: буфер vs допсоглашение |
| **Автор (через куратора)** | Text / User picker | — | Легитимность вброса |
| **Оценка (SP)** | Number | — | Трудозатраты |
| **WSJF: Ценность** | Number | 1–5 | Приоритет |
| **WSJF: Срочность** | Number | 1–5 | Приоритет |
| **WSJF: Снижение риска** | Number | 1–5 | Приоритет |
| **Приоритет (WSJF)** | Scripted field (ScriptRunner) | вычисляемое | Очередь буфера |
| **Маршрут CCB** | Select | Буфер / След. инкремент / Изм. контракта / Отклонено / Объединено | Решение CCB |
| **Веха** | Version picker (fixVersion) | — | Связь с контрактом |
| **Влезает в буфер** | Checkbox / Select | Да / Нет | Оценка влияния |
| **Что двигаем** | Text (multi) | — | Оценка влияния |
| **Сдвиг вехи (дней)** | Number | — | Влияние на срок |

> Держите набор минимальным. Обязательными на форме создания делайте только «Суть», «Автор» и «Заявленная срочность» — остальное заполняется на шагах классификации и оценки, иначе регистрация вброса становится тяжёлой и его будут обходить (антипаттерн «вброс мимо процесса», [17](17_АНТИПАТТЕРНЫ_И_КЕЙСЫ.md)).

## Workflow «Запроса на изменение»

Статусы повторяют воронку Единого окна из [04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md): регистрация → классификация → оценка → решение CCB → маршрут.

```
                    ┌──────────────┐
   создание  ──────►│  НОВЫЙ        │  (шаг 1: регистрация)
                    └──────┬───────┘
                           │ классифицировать
                           ▼
                    ┌──────────────┐
                    │ КЛАССИФИКАЦИЯ │  (тип, критичность, связь с контрактом)
                    └──────┬───────┘
                           │ оценить влияние
                           ▼
                    ┌──────────────┐
                    │  ОЦЕНКА       │  (SP, что двигаем, WSJF)
                    └──────┬───────┘
                           │ вынести на CCB
                           ▼
                    ┌──────────────┐
             ┌──────│  НА CCB       │──────┐
             │      └──────┬───────┘      │
     маршрут │           │ маршрут       │ маршрут
             ▼           ▼               ▼
    ┌─────────────┐ ┌──────────────┐ ┌──────────────┐   ┌────────────┐
    │  В БУФЕРЕ    │ │ В ИНКРЕМЕНТ  │ │ ДОПСОГЛАШЕНИЕ │   │ ОТКЛОНЁН/  │
    │  (в работе) │ │ (отложен)    │ │ (ждёт юр.)   │   │ ОБЪЕДИНЁН   │
    └──────┬──────┘ └──────┬───────┘ └──────┬───────┘   └─────┬──────┘
           │               │                │                 │
           └───────────────┴────► ГОТОВО ◄──┘                 ▼
                              (выполнен, прошёл DoD)        ЗАКРЫТ
```

**Fast-track P1** ([03](03_ЖИЗНЕННЫЙ_ЦИКЛ.md)): отдельный переход «Взять как P1» из статуса «Новый» сразу в «В буфере (в работе)» с обязательной постфункцией — проставить метку `P1`, зафиксировать время, создать напоминание о ратификации на ближайшем CCB.

### Контроль на переходах (валидаторы и постфункции ScriptRunner)

| Переход | Валидатор (условие) | Постфункция (действие) |
|---------|---------------------|------------------------|
| Новый → Классификация | Заполнена «Суть», указан «Автор через куратора» | — |
| Классификация → Оценка | Заполнены «Тип вброса», «Критичность», «В объёме контракта» | — |
| Оценка → На CCB | Заполнены «Оценка (SP)» и три фактора WSJF | Пересчитать «Приоритет (WSJF)»; запустить детектор подмены (см. скрипт ниже) |
| На CCB → любой маршрут | Заполнено поле «Маршрут CCB»; для «Допсоглашение» — «В объёме контракта = Нет» | Записать дату решения, автора |
| Любой → Готово | Пройден DoD-чеклист (все пункты отмечены) | Проставить дату завершения |

> Валидаторы — цифровой аналог DoR/DoD ([10](10_КАЧЕСТВО_И_DOD.md)): не пускают задачу дальше, пока не выполнены критерии готовности этого шага.

### Постфункция: детектор подмены классификации

Реализует «красные флаги» переклассификации из [04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md).

> **Где ставить — важно.** Детектор сравнивает заявленный тип с **трудозатратами**, а поле «Оценка (SP)» заполняется на шаге «Оценка». Поэтому постфункция ставится на переход **Оценка → На CCB**, а не на «Классификация → Оценка»: на предыдущем шаге SP ещё пусто, и флаг не сработает никогда. Смысл сохраняется — вброс с сомнительной классификацией помечается **до** решения CCB, то есть до того, как маршрут выбран.

```groovy
// ScriptRunner → Workflow → Post Function (Custom script post-function)
// Переход: "Оценка → На CCB" (после того как заполнена Оценка (SP)).
// Флаг: "Уточнение/Дефект" с заметными трудозатратами → подсветить как
// возможную скрытую "новую функцию" (объём сверх контракта).
import com.atlassian.jira.component.ComponentAccessor

// Условный порог "заметных трудозатрат" — задаётся командой (напр. > 4 SP ≈ ½ дня+)
final BigDecimal SP_THRESHOLD = 4
final String FLAG_LABEL = "проверить-переклассификацию"
final List<String> SUSPECT_TYPES = ["Уточнение", "Дефект"]

def cfm = ComponentAccessor.customFieldManager

// --- Имена полей адаптируйте под свою инсталляцию ---
def typeField = cfm.getCustomFieldObjectsByName("Тип вброса")?.first()
def spField   = cfm.getCustomFieldObjectsByName("Оценка (SP)")?.first()
if (!typeField || !spField) {
    return // поля не найдены — молча выходим, чтобы не ломать переход
}

def typeVal = issue.getCustomFieldValue(typeField)?.toString()
def spVal   = issue.getCustomFieldValue(spField) as BigDecimal

if (!(typeVal in SUSPECT_TYPES) || spVal == null || spVal <= SP_THRESHOLD) {
    return // подозрений нет
}

def currentUser = ComponentAccessor.jiraAuthenticationContext.loggedInUser

// 1. Метка-флаг для JQL-ревизии менеджером изменений
def labelManager = ComponentAccessor.getComponent(com.atlassian.jira.issue.label.LabelManager)
labelManager.addLabel(currentUser, issue.id, FLAG_LABEL, false)

// 2. Комментарий-подсказка с объяснением, почему сработало
ComponentAccessor.commentManager.create(issue, currentUser,
    "⚠️ Детектор подмены: тип «${typeVal}» при оценке ${spVal} SP (порог ${SP_THRESHOLD}). " +
    "Проверьте перед CCB — возможно, это НОВАЯ ФУНКЦИЯ (объём сверх контракта), а не деталь. " +
    "См. раздел 04 «Детектор подмены классификации».", false)
```

> Скрипт рабочий по логике, но требует адаптации: подставьте фактические имена полей (или `getCustomFieldObject("customfield_XXXXX")`), проверьте на тестовом стенде и вынесите `SP_THRESHOLD` в конфиг команды. `addLabel(..., false)` не рассылает уведомления — метка служебная, комментарий уже оповещает.

> Детектор — **подсказка, а не автомат**: он ставит флаг, а переклассифицирует вброс менеджер изменений. Классификацию по-прежнему определяет суть работы, оценённая человеком ([04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md)).

## JQL-запросы для ключевых представлений

Готовые к копированию фильтры. Всё — в **одном проекте** (замените ключ `GRN` на свой). Потоки различаются **типом задачи и меткой**, а не отдельными проектами. Названия полей в `cf[...]`/`"Имя поля"` подставьте свои; в Jira Server имена кастомных полей в JQL допустимо писать в кавычках, при неоднозначности используйте `cf[12345]`.

**Очередь буфера, упорядоченная по приоритету (упрощённый WSJF):**
```sql
project = GRN AND issuetype = "Запрос на изменение"
AND "Маршрут CCB" = "Буфер" AND status = "В буфере (в работе)"
ORDER BY "Приоритет (WSJF)" DESC
```

**Вбросы, ожидающие решения CCB (повестка заседания):**
```sql
project = GRN AND issuetype = "Запрос на изменение" AND status = "На CCB"
ORDER BY "Критичность" ASC, created ASC
```

**Реестр изменений целиком (единый журнал вбросов, [09](09_ШАБЛОНЫ.md)):**
```sql
project = GRN AND issuetype = "Запрос на изменение" ORDER BY created DESC
```

**«Зависшие» новые вбросы дольше 2 дней (риск обхода процесса):**
```sql
project = GRN AND issuetype = "Запрос на изменение" AND status = "Новый"
AND created <= -2d
```

**Все P1 за последние 2 месяца (контроль fast-track и ратификации):**
```sql
project = GRN AND issuetype = "Запрос на изменение" AND "Критичность" = P1
AND created >= startOfMonth(-2) ORDER BY created DESC
```

**Кандидаты в детектор подмены (для ревизии менеджером изменений):**
```sql
project = GRN AND issuetype = "Запрос на изменение"
AND "Тип вброса" in ("Уточнение", "Дефект") AND "Оценка (SP)" > 4
```

**Вбросы, требующие допсоглашения (объём сверх контракта):**
```sql
project = GRN AND issuetype = "Запрос на изменение"
AND "Маршрут CCB" = "Изм. контракта" AND statusCategory != Done
```

**Расход буфера в текущем спринте (задачи, взятые из вбросов):**
```sql
project = GRN AND labels = вброс AND sprint in openSprints()
ORDER BY updated DESC
```

**Дефекты вне буфера (обязательство по качеству, не расходуют буфер):**
```sql
project = GRN AND issuetype = Дефект AND sprint in openSprints()
```

**Контрактный поток текущей вехи (без вбросов):**
```sql
project = GRN AND fixVersion = "Веха 3" AND (labels is EMPTY OR labels != вброс)
AND issuetype in (История, Задача) ORDER BY status
```

**🔴-риски без владельца (триггер эскалации, [11](11_УПРАВЛЕНИЕ_РИСКАМИ.md)):**
```sql
project = GRN AND issuetype = Риск AND "Уровень риска" >= 13 AND assignee is EMPTY
```

**Реестр техдолга (тренд, [05](05_ПЛАНИРОВАНИЕ_И_БУФЕРЫ.md)):**
```sql
project = GRN AND issuetype = Техдолг AND statusCategory != Done ORDER BY priority DESC
```

**Задачи, «застрявшие» на DoD (в статусе Review дольше 3 дней):**
```sql
project = GRN AND status = "Review" AND status changed before -3d
```

> Сохраните каждый запрос как **именованный фильтр** и раздайте права ролям (менеджер изменений, РП, владелец продукта). Фильтры — топливо и для досок (каждая доска = проект + JQL-фильтр), и для дашбордов ниже. Именно фильтры, а не отдельные проекты, разделяют потоки.

### JQL-функции ScriptRunner (расширенные выборки)

ScriptRunner добавляет полезные JQL-функции, недоступные штатно (всё в пределах одного проекта):
```sql
-- вбросы, у которых поле "Маршрут CCB" когда-либо менялось (аудит решений CCB)
issueFunction in changedFields("Маршрут CCB") AND issuetype = "Запрос на изменение"

-- контрактные задачи, связанные с вбросом (трассировка объёма)
issueFunction in linkedIssuesOf("issuetype = 'Запрос на изменение'", "relates to")
AND issuetype in (История, Задача)
```

Готовность вехи к гейту соответствия проверяется **штатным** JQL по версии — функция ScriptRunner здесь не нужна и не поможет: вехи в ГРАНИТ замаплены на версии (`fixVersion`), а `epicsOf` возвращает эпики, а не версии.

```sql
-- незакрытые дефекты текущей вехи (блокируют гейт соответствия)
project = GRN AND fixVersion = "Веха 3" AND issuetype = Дефект AND statusCategory != Done
```

> Если вехи у вас реализованы эпиками, а не версиями, то для «эпиков с незакрытыми дефектами» подойдёт `issueFunction in epicsOf("issuetype = Дефект AND statusCategory != Done")`. Проверьте свой маппинг по таблице выше, прежде чем копировать запрос.

## Дашборды: панель здоровья процесса

Панель здоровья из [07](07_МЕТРИКИ.md) собирается на штатных гаджетах Jira + фильтрах выше. Один дашборд «Здоровье контракта» на команду и заказчика.

Все гаджеты питаются от **именованных фильтров** (по типу задачи и метке) в рамках одного проекта — не от отдельных проектов.

| Метрика ([07](07_МЕТРИКИ.md)) | Гаджет Jira | Источник (фильтр в одном проекте) |
|-------------------------------|-------------|----------|
| Прогноз ближайшей вехи | Release/Version Report, Roadmap | Версии = вехи |
| Расход буфера вбросов | Two Dimensional Filter Statistics / Pie (сумма SP по метке `вброс` в спринте) | Фильтр расхода буфера |
| Частота вбросов (тренд) | Created vs Resolved Chart | Фильтр `issuetype = "Запрос на изменение"` |
| Структура решений CCB | Pie Chart по полю «Маршрут CCB» | Реестр изменений (фильтр вбросов) |
| Предсказуемость (Say/Do) | Sprint Health / Velocity Chart | Доска «Разработка» |
| Скорость (velocity) | Velocity Chart | Доска «Разработка» |
| Время до решения по вбросу | Average Age Chart / Time in Status (ScriptRunner) | Фильтр вбросов на CCB |
| Индекс перегрузки команды | Внешний расчёт (сверхурочные) → отметка на дашборде | Учёт времени / Tempo |
| 🔴-риски / bus factor = 1 | Filter Results по фильтру рисков | Фильтр `issuetype = Риск` |
| Дефекты после приёмки | Filter Results / Pie по дефектам | Фильтр `issuetype = Дефект` |

> **Зонные цвета (🟢🟡🔴) буфера** штатными гаджетами напрямую не рисуются. Варианты: (а) считать процент расхода scripted-полем и подсвечивать через **Wallboard**-стиль, (б) выносить fever-chart буфера в отдельный отчёт (ScriptRunner scripted-fragment или выгрузка в BI). Ключевой принцип из [05](05_ПЛАНИРОВАНИЕ_И_БУФЕРЫ.md) — расход **относительно % готовности вехи** — почти всегда требует кастомного расчёта, штатного гаджета для fever-chart нет.

> У каждого гаджета — свой **владелец** ([07](07_МЕТРИКИ.md)): дашборд без ответственного за реакцию превращается в «обои». Метрика без решения бесполезна.

## Автоматизация на ScriptRunner

> Всё в этом разделе требует **установленного ScriptRunner for Jira** (см. «Предпосылки»). Без него — ручной расчёт или штатные средства.

### 1. Scripted-поле «Приоритет (WSJF)»

Автоматический расчёт упрощённого приоритета из [04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md): `(Ценность + Срочность + Снижение риска) / Трудозатраты`.

```groovy
// ScriptRunner → Fields → Scripted Field (тип: Number)
// Пересчитывается при отображении/индексации задачи.
import com.atlassian.jira.component.ComponentAccessor

def cfm = ComponentAccessor.customFieldManager
def value    = issue.getCustomFieldValue(cfm.getCustomFieldObjectByName("WSJF: Ценность")) as Double
def urgency  = issue.getCustomFieldValue(cfm.getCustomFieldObjectByName("WSJF: Срочность")) as Double
def risk     = issue.getCustomFieldValue(cfm.getCustomFieldObjectByName("WSJF: Снижение риска")) as Double
def sp       = issue.getCustomFieldValue(cfm.getCustomFieldObjectByName("Оценка (SP)")) as Double

if ([value, urgency, risk, sp].any { it == null } || sp == 0) {
    return null // недостаточно данных или защита от деления на ноль
}
return ((value + urgency + risk) / sp).round(2)
```

> Это **не** канонический WSJF из SAFe, а авторское упрощение ГРАНИТ ([04](04_УПРАВЛЕНИЕ_ИЗМЕНЕНИЯМИ.md)). Поле используется только для упорядочивания очереди буфера, а не как жёсткий автомат — финальное решение за CCB.

### 2. Запланированное задание: напоминание о просроченном решении CCB

Реализует контроль «Время до решения по вбросу» ([07](07_МЕТРИКИ.md)) и сроки fast-track ([03](03_ЖИЗНЕННЫЙ_ЦИКЛ.md)): P2 — решение в течение суток, P3 — на ближайшем еженедельном CCB.

```groovy
// ScriptRunner → Escalation Service / Scheduled Job (запуск раз в день/час)
// JQL задания: вбросы, зависшие в ожидании решения дольше нормы (один проект, фильтр по типу).
// P2 не решённые за сутки:
//   project = GRN AND issuetype = "Запрос на изменение" AND "Критичность" = P2
//   AND status = "На CCB" AND updated <= -1d
// Действие: уведомить РП и куратора, поднять флаг.
import com.atlassian.jira.component.ComponentAccessor

def cmm = ComponentAccessor.commentManager
def user = ComponentAccessor.jiraAuthenticationContext.loggedInUser
cmm.create(issue, user,
    "⏰ Просрочено решение по вбросу (критичность превышает норму реакции). " +
    "Эскалация на уровень 3 (CCB) — см. раздел 12. Автор напоминания: система ГРАНИТ.",
    false)
// + отправка e-mail через ComponentAccessor.getMailQueue() или встроенное действие Escalation Service
```

### 3. Слушатель: эскалация по зонам буфера / вехи

Автоматическая эскалация из [12](12_СТЕЙКХОЛДЕРЫ_И_КОММУНИКАЦИИ.md): прогноз вехи ушёл в 🔴 или буфер в 🔴/⚫ → уведомить CCB. Реализуется запланированным заданием, считающим расход буфера в открытом спринте и сравнивающим с зонами из [05](05_ПЛАНИРОВАНИЕ_И_БУФЕРЫ.md).

Реализует **правило зоны fever chart** из [05](05_ПЛАНИРОВАНИЕ_И_БУФЕРЫ.md) буква в букву: зона определяется расходом буфера **и** опережением прогресса вехи (пороги 30/15 п.п.).

```groovy
// ScriptRunner → Scheduled Job (раз в день)
// Считает зону буфера по правилу fever chart из раздела 05 и эскалирует 🔴/⚫ на CCB.

// --- Входные данные (получите из своей модели) ---
def BUFFER_SP = 8.0            // выделенный буфер вбросов на итерацию (из плана инкремента)
def usedSp = 6.0               // сумма SP задач с меткой "вброс" в openSprints() — через SearchService
def milestoneReadiness = 0.30  // готовность вехи, 0..1 — из прогресса версии (fixVersion)

// --- Пороги правила зоны (раздел 05; фиксируются командой, не меняются "на глаз") ---
final BigDecimal RED_SPEND   = 0.67   // расход, с которого зона красная
final BigDecimal YELLOW_SPEND = 0.34  // расход, с которого зона жёлтая
final BigDecimal RED_LEAD    = 0.30   // опережение прогресса для красной зоны (30 п.п.)
final BigDecimal YELLOW_LEAD = 0.15   // опережение прогресса для жёлтой зоны (15 п.п.)

def spend = usedSp / BUFFER_SP                 // 0.75 — доля израсходованного буфера
def lead  = spend - milestoneReadiness         // 0.45 — насколько расход обогнал прогресс

def zone
if (spend > 1.0) {
    zone = "⚫ пробой"
} else if (spend >= RED_SPEND || lead > RED_LEAD) {
    zone = "🔴 красная"
} else if (spend >= YELLOW_SPEND || lead > YELLOW_LEAD) {
    zone = "🟡 жёлтая"
} else {
    zone = "🟢 зелёная"
}

if (zone in ["🔴 красная", "⚫ пробой"]) {
    // создать/обновить задачу-эскалацию для CCB, уведомить РП и куратора;
    // в тексте указать: зона, расход (spend), готовность вехи, опережение (lead)
}
```

> Способ получения `usedSp` (поиск по метке `вброс` в открытом спринте) и `milestoneReadiness` (прогресс версии) адаптируйте под свою модель. Пороги и логика зон — строго из [05](05_ПЛАНИРОВАНИЕ_И_БУФЕРЫ.md) и [07](07_МЕТРИКИ.md); не изобретайте свои шкалы, иначе автоматизация начнёт расходиться с тем, что обсуждается на CCB.

### 4. Behaviours: контроль DoR на форме и обязательность полей по шагам

ScriptRunner **Behaviours** позволяют делать поля обязательными **контекстно** — не на создании (чтобы не тормозить регистрацию), а на нужном шаге:
- На создании обязательны только «Суть» и «Автор через куратора».
- Поля классификации становятся обязательными при переходе в статус «Классификация».
- Поля WSJF и «Оценка (SP)» — обязательны для перехода «На CCB».

Это цифровая реализация **DoR как входного фильтра** ([10](10_КАЧЕСТВО_И_DOD.md)): задача не уедет дальше по воронке, пока не готова к этому шагу.

### Что можно без ScriptRunner (деградация функционала)

| Функция | С ScriptRunner | Без него (штатно) |
|---------|----------------|-------------------|
| Расчёт WSJF | Scripted-поле, авто | Ручной ввод в числовое поле |
| Детектор подмены | Постфункция-подсветка | Ручная ревизия по JQL-фильтру |
| Эскалация по зонам | Scheduled Job | Ручной контроль на CCB |
| Напоминания о просрочке | Escalation Service | Штатные подписки на фильтр (Subscription) |
| Контекстная обязательность | Behaviours | Обязательные поля схемы (грубее, тормозят вход) |

> Даже полностью «ручной» вариант на штатной Jira работоспособен на уровне зрелости L2–L3. ScriptRunner нужен для перехода к L4–L5 (автоматизация и метрики, [19](19_МОДЕЛЬ_ЗРЕЛОСТИ.md)).

## Отечественные аналоги (импортозамещение)

Поскольку Jira для новых проектов в РФ, как правило, недоступна легально и не проходит требования реестрового ПО ([15](15_ИМПОРТОЗАМЕЩЕНИЕ.md)), маппинг ГРАНИТ переносится на отечественные трекеры. **Принципы универсальны** — меняется только реализация.

| Механизм ГРАНИТ | Что искать в любом трекере |
|-----------------|----------------------------|
| Единое окно | Отдельная **доска/представление** для входящих запросов (в общем пространстве, не обязательно отдельный проект) |
| Типы задач (вброс/риск/техдолг) | Настраиваемые типы задач |
| Workflow воронки CCB | Настраиваемые статусы и переходы |
| Кастомные поля карточки влияния | Пользовательские поля |
| Приоритизация (WSJF) | Числовые поля + формульные/вычисляемые поля или ручной расчёт |
| Автоматизация (эскалации, напоминания) | Встроенные правила автоматизации / вебхуки / скрипты |
| Дашборды панели здоровья | Виджеты/отчёты/BI-интеграция |

Отечественные трекеры, применимые под ГРАНИТ (проверяйте актуальный статус в реестре отечественного ПО и соответствие вашему контракту на момент проекта): **Яндекс Трекер, Kaiten, YouGile, EvaTeam, Аврора (Naumen), Bpium, Elma365, Pyrus** и др. Наличие в реестре Минцифры и класс защищённости — обязательный критерий выбора для контрактов с требованием импортозамещения.

> Выбор трекера — часть реестра технологического стека ([15](15_ИМПОРТОЗАМЕЩЕНИЕ.md)) и архитектурных решений (ADR, [14](14_ЗНАНИЯ_И_КОМАНДА.md)). Если трекер входит в состав поставки заказчику (а не только внутренний инструмент команды) — он обязан соответствовать требованиям контракта к ПО.

## Антипаттерны инструментализации

Цифровые версии «граблей» из [17](17_АНТИПАТТЕРНЫ_И_КЕЙСЫ.md):

- 🚫 **Over-engineering workflow.** 15 статусов и 20 обязательных полей «на всякий случай». Убивает скорость входа → вбросы идут мимо процесса. **Противоядие:** статусов ровно под воронку CCB, обязательность — контекстная (Behaviours).
- 🚫 **Обязательные поля-убийцы на создании.** Если для регистрации вброса нужно заполнить 12 полей — команда перестанет регистрировать. **Противоядие:** на входе только «Суть» + «Автор через куратора».
- 🚫 **Дашборд без владельца.** Панель есть, но на 🔴 никто не реагирует. **Противоядие:** у каждого гаджета — владелец и церемония ([07](07_МЕТРИКИ.md)).
- 🚫 **Автоматизация вместо решения.** Скрипт сам меняет маршрут вброса или сам «одобряет» — подменяет коллегиальное решение CCB. **Противоядие:** автоматика **готовит и подсвечивает**, решение принимает CCB под протокол (принцип 9, [01](01_ПРИНЦИПЫ.md)).
- 🚫 **Инструмент как источник правды вместо контракта.** Статус в Jira «Готово» не равен подписанному акту. **Противоядие:** юридические документы (протоколы CCB, акты) — вне трекера, трекер лишь отражает процесс.
- 🚫 **Зоопарк проектов.** Отдельный проект под вбросы, отдельный под риски, отдельный под техдолг — дубли схем полей/статусов/прав, сложные связи-переносы, рассинхрон. **Противоядие:** один проект, разделение потоков через тип задачи + метки + доски и JQL. Отдельный проект оправдан только принципиально иным жизненным циклом или требованиями безопасности/прав, а не «чтобы не мешалось».
